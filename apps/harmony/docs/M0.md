# 鸿蒙端 M0：原生工具链（Refs #241）

目标：在没有真机、没有 DevEco 的 Linux aarch64 主机上，证明 mihomo 内核能编成 OHOS 可 dlopen 的 `libzmihomo.so`。

## 版本与来源

| 组件 | 版本 | 来源 / 校验 |
|---|---|---|
| sysroot | OpenHarmony 6.1-Release SDK，native 6.1.0.31，API 23 | `https://repo.huaweicloud.com/openharmony/os/6.1-Release/ohos-sdk-windows_linux-public.tar.gz`，SHA256 `b833b75a64ee46bbd7880921abbb49b733ec5c8171b6684c9b524d57f624cee0` |
| clang/lld | 19.1.7（Debian trixie 包，dpkg -x 解到用户目录） | 与 SDK sysroot 拼成混合 NDK：`$OHOS_TOOLS/ohos-ndk-arm64` |
| Go | Paws go-patch go1.27.3（`GOOS=openharmony`，arm64 shared 走 TLSDESC） | tarball SHA256 `e116579274f1cf446b4916f85d978e236dc500246f8062fffd5f9ed9ae4bb05d` |
| Rust | 1.90.0 + `aarch64-unknown-linux-ohos` | rustup |

x86_64 / macOS 主机可直接把 `OHOS_NDK_HOME` 指向 DevEco 的 `sdk/default/openharmony/native`。

## 构建

```bash
source apps/harmony/native/scripts/env.sh
apps/harmony/native/scripts/experimental-build-mihomo.sh --probe arm64   # 最小探针库
apps/harmony/native/scripts/experimental-build-mihomo.sh arm64           # 完整 libzmihomo.so
apps/harmony/native/scripts/check-ohos-so.sh apps/harmony/native/out/arm64-v8a/libzmihomo.so
```

关键参数：`GOOS=openharmony GOARCH=arm64 CGO_ENABLED=1 GOTOOLCHAIN=local`，`CC=$GOROOT/ohos-scripts/cc-arm64`，`CGO_CFLAGS=-ftls-model=global-dynamic`，tags `with_gvisor`，不加 `netgo`，c-shared。

gVisor：OHOS 的 SELinux 拒绝对系统交来的 TUN fd 做 fstat（`unix.Fstat(..) failed: permission denied`）。脚本在构建目录里拷一份 `github.com/metacubex/gvisor v0.0.0-20260922041103-e2cbcd6e7400`，打 `scripts/patches/gvisor-fstat-tun.patch`（`fdbased.IsSocketFD` 遇 EACCES/EPERM 视为非 socket），再 `go mod edit -replace`。仓库里的 `mihomo-mobile/go.mod` 不改。正式方案由 A 在 #244 落到 `tools/build-mihomo.sh`。

## 结果（2026-11-19，沙箱 aarch64）

- `libzprobe.so`（2,233,952 字节）：PASS。
- `libzmihomo.so`（73,793,184 字节，未压缩）：PASS。
  - TLS 重定位只有 1 条 `R_AARCH64_TLSDESC`，无 `TLS_TPREL` / `TLSLE` / `TLSIE`。
  - PT_TLS 0x10，无 `DF_STATIC_TLS`。
  - `DT_NEEDED` 只有 `libc.so`；SONAME `libzmihomo.so`；期望的 12 个 `zm_*` 导出都在。

为何必须如此：OHOS 的 musl 对 dlopen 库中的 initial-exec TLS 硬拒绝（`initial-exec TLS resolves to dynamic definition`），而 `GOOS=android` 在 ArkTS 线程上会 SIGSEGV。

## 风险

- 防回环：`protectProcessNet` / `blockedApplications` 不够（同类项目出现 4 万多 goroutine、>1 GiB），依赖 A 的 `zm_set_socket_hook`（#243）逐 socket 绑物理网络，fail-closed。
- mihomo UDP 回环检测会用 netlink 列网卡，OHOS 上被拒，需要关掉。
- 产物 73 MB 未压缩，HAP 体积需关注。

## core-ohos（napi-ohos 薄层，2026-11-20）

位置 `apps/harmony/native/core-ohos/`：独立 Cargo workspace，`cdylib`，产物 `libcore_ohos.so`，依赖 `core-mobile`（path）与 `napi-ohos 1.2`（`napi8`、`tokio_rt`）/ `napi-derive-ohos` / `napi-build-ohos`。类型声明手写在 `index.d.ts`。

导出（ArkTS：`import core from 'libcore_ohos.so'`）：

| 导出 | 转发到 | 说明 |
|---|---|---|
| `version()` | core-ohos 包版本 | core-mobile 没有版本函数 |
| `greeting()` | `engine::core_greeting` | zephyr-core 链接探针 |
| `new MobileCore(dataDir)` | `MobileCore::new` | 出错抛 Error |
| `subscriptionsSummary()` | `MobileCore::subscriptions_summary` | 同步 |
| `rebuildMockNodes(scale)` | `MobileCore::rebuild_mock_nodes` | Promise；tokio `spawn_blocking`，不占 ArkTS 线程 |

构建：`apps/harmony/native/core-ohos/build.sh`（release，拷到 `out/arm64-v8a/` 并跑 `check-ohos-so.sh`）。目标链接器用 NDK 的 `aarch64-unknown-linux-ohos-clang`。aarch64 沙箱没有系统 `cc`，脚本在 `native/build/`（gitignore）里生成主机 `cc` 包装：llvm19-root 的 clang，sysroot 拼成 `usr → llvm19-root/usr`、`lib → 主机 /lib`（root 里缺 `libm.so.6`、`libgcc_s.so.1` 等运行时库），并加 `-Wl,--no-mmap-output-file`（gVisor 下 lld 偶发 SIGBUS）。

结果（沙箱 aarch64）：`libcore_ohos.so` 4,785,184 字节，PASS。
- 无 TLS 重定位、无 PT_TLS、无 `DF_STATIC_TLS`。
- `DT_NEEDED`：`libace_napi.z.so`、`libc.so`；不需要 `libc++_shared.so`。SONAME `libcore_ohos.so`。
- `napi_module_register`（UND）由 `.init_array` 构造函数调用；导出 `napi_register_module_v1`。
